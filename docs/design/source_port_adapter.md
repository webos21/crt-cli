# D3 Design: Native Source-port Recipe Adapter (zlib first)

Status (2026-11-09): **bounded zlib implementation has native Linux/x86_64,
macOS/arm64 and Windows/x64 evidence, and its bounded CRT contract is approved
and adopted.** See the [adoption decision](../compatibility.md#d3-bounded-adapter-adoption-2026-11-09). The original slice below is retained as design history;
project providers/port locks and OS adapters are now implemented where acceptance
records them. Other recipes, generic resolution and Windows/arm64 D3 remain separate.
The current closure/handoff procedure is in the [development guide](../guides/development.md#d3-common-change-closure-and-native-handoff).
The original scope and proposed extensions below are not all implemented. A command, store layout or manifest is a current CLI contract only where the matching
[acceptance](../acceptance/sdk_install_acceptance.md) record exists. The architecture, build-key rule and
non-negotiable constraints stay owned by [the CLI design](crt_cli.md#5-source-first-port-recipe-engine); this
document only fixes what the *first slice* means, so that producer and consumer can build it in parallel. The
producer-side obligations are mirrored in the
[SDK contract](https://github.com/webos21/crt/blob/main/docs/design/sdk_development_contract.md#d3-source-port-adapter-producer-obligations-2026-11-06).

## 1. Scope of the first slice

Build the reviewed `zlib` 1.3.1 recipe (`porting/recipes/zlib.json`, recipe format `schema_version: 1`) from its
pinned upstream source, **natively in `crt-cli`**, on **Linux/x86_64** first, into a separate immutable port-store item,
and prove that a consumer links and runs against those bytes in both the static and the shared case.

In scope: fetch-or-seed and verify the source, pristine copy, configure/make/install in a job directory, the recipe's
own `tests`, a binary audit, atomic store publish, and a consumer proof.

Originally out of scope for the initial Linux slice (not a current capability list): registry/index resolution and channels, any recipe whose
`build.system` is not `configure`, dependency ports (SQLite, libpng-to-zlib), project `crt.json`/`crt.lock` fields for
ports, `--locked`/`--offline` project semantics, trusted binary caches, other hosts. Windows CRT-shell/make static/shared
remains a required gate for **full** D3 closure (TODO 4.2); this slice must not be written so that it blocks it (§7).

## 2. Decisions

### D3-1. The executor is native; `crt-port-build.py` is the oracle, not a dependency

The owner selected native CLI execution on 2026-10-28 and the CLI must not require Python, CMake or a shell on the
host ([SDK contract](https://github.com/webos21/crt/blob/main/docs/design/sdk_development_contract.md)). The packaged
`tools/crt-port-build.py` therefore stays the producer's reference implementation: it defines the *meaning* of recipe
fields, and its result for zlib is the differential baseline (§6). The CLI never invokes it, and does not copy its
internal module APIs.

### D3-2. Fail closed on a bounded recipe subset

The slice executes exactly the recipe subset that `zlib.json` uses and refuses everything else with a diagnostic naming
the field, instead of ignoring it:

| Recipe field | Slice-1 handling |
|---|---|
| `schema_version` | must be `1` |
| `name`, `version` | identity; recorded in the store manifest |
| `source.url/archive/source_dir/sha256` | `sha256` is the only trust anchor and is mandatory; `sha1`/`md5` are informational and, when present, must also match |
| `dependencies` | classified by role (D3-3), never by name |
| `build.system` | only `configure`; anything else is refused |
| `build.configure_args`, `build.make_args` | argv elements, substituted (placeholders below) |
| `build.env`, `target_overrides.<os>.env` | exact merge order of the oracle: base, then OS override; flag variables (`CFLAGS`...) accumulate as in the oracle |
| `build.post_configure_patch[]` | exact first-occurrence `find`/`replace` on a **generated** file under the job work tree; a missing `find` text fails the build |
| `tests[]` | `type: compile-run` only; `source`, `cflags`, `link_args`, `expect_stdout`, OS override of `link_args` |
| `status`, `notes` | ignored (documentation) |
| any other key or placeholder | refused |
| `target_overrides.<os>` | only `linux`, `macos`, `windows` are recognised; only the running OS is applied (D3 §7) |

Placeholders accepted in the slice: `@PORT_PREFIX@`, `@PORT_PREFIX_POSIX@`, `@PORT_PREFIX_MAKE@` (the POSIX prefix with
each space backslash-escaped), `@CC@`. A recipe whose bytes differ from a reviewed digest (D3-3) is not executed.

`post_configure_patch` edits a file *generated by upstream's configure* in the job copy. It is not an edit of upstream
source, so it does not need the source-patch exception review, but it is a recorded workaround: its `reason` is copied
into the store manifest and it is removed when upstream's generated Makefile quotes `prefix` correctly (long-term
removal condition, owned by the recipe).

### D3-3. Roles come from a CRT-reviewed table keyed by recipe digest, not from names

`zlib.json` lists `make` under `dependencies`. That is a **host tool**, not a target library
([CLI design](crt_cli.md#reuse-existing-assets)). The CLI must not infer this from the name. The recipe JSON is pinned by
digest and is not rewritten; so the role and SDK-requirement metadata live in a small **reviewed adapter table** that
CRT owns and the CLI embeds for the slice:

```text
recipe_sha256 -> { name, version,
                   host_tools: ["make"],          # resolved in the pinned host-tools bundle inventory
                   target_ports: [],              # none for zlib
                   sdk_requirements: { stage: ">=01-c" (Dev SDK satisfies), cc: "crt-cc" },
                   variants: ["static", "shared"] }
```

An unknown recipe digest is refused. This table is the seed of the later registry index; it is *not* a new recipe
format. Adding an optional field to the recipe JSON instead is rejected for now: it would change a pinned, shared
format and force a coordinated producer/consumer migration for no slice-1 benefit.

### D3-4. SDK-provided zlib versus an isolated source build

The Dev SDK already ships `include/zlib.h`, `lib/libz.a` and `libz.so*`. Rule, for slice 1 and as the shape for later work:

1. A project dependency named `zlib` resolves to **exactly one provider**: `sdk` (default; no build, the SDK's bytes
   are used as shipped) or `port` (explicit isolated source build). The choice is explicit and recorded; it is never
   inferred from "the build worked".
2. A `port` provider is never installed into an SDK directory. Its bytes live only in
   `ports/store/<build-key>/` and the SDK stays byte-identical (verified by `sdk verify` before and after).
3. When the provider is `port`, the project's compile/link contract puts the port `include/` and `lib/` **in place of**
   the SDK's zlib, not merely before it. A consumer closure that can reach both an SDK `libz` and a port `libz` is an
   error (one ABI per runtime closure, per [CLI design](crt_cli.md#execution-and-installation)).
4. Linking the SDK's existing `libz` is **not** counted as a first source port (TODO D3).

### D3-5. Environment and toolchain for the slice

* **Compiler:** the SDK's public `tools/crt-cc` / `tools/crt-c++` wrappers (POSIX `sh` scripts) are the `CC`/`CXX` the
  recipe's `configure` sees. `configure` needs a command string; the native compiler module's argument templates are not
  a command. Re-deriving them as a CLI compiler bridge is deferred, and this is recorded as a deliberate reuse of an
  existing SDK public entry point (SDK contract table: "Delegate startup/sysroot/ABI/link policy"), not an accident.
* **Shell, make, coreutils:** only from the **pinned independent host-tools bundle** through the existing
  `port-build` profile (`--host-tools`, `--host-tools-sha256`, `--work-root` must be a new job path outside the bundle
  and the SDK). No silent fallback to the host `/bin/sh` or `make`: that would not exercise the path Windows must use.
* **Target/triple/sysroot:** from the verified, installed SDK identity (`CRT_SYSROOT`, `CRT_TARGET_OS`,
  `CRT_TARGET_ARCH`); the executor sets no other host-derived value.
* **Compilers LLVM/lld:** the same user-declared external toolchain as app builds; unchanged.
* **Archiver/ranlib:** the pinned external LLVM `llvm-ar`/`llvm-ranlib` (as the oracle prefers), recorded in the build key.

The environment is built per job, from scratch, and contains only the variables the oracle exports for a configure
port (`CC CXX AR RANLIB CFLAGS CPPFLAGS CXXFLAGS LDFLAGS LIBS CRT_*` plus recipe `env`). Nothing is inherited implicitly
(the recorded list is part of the build key's "relevant declared environment").

### D3-6. Source handling

* Source bytes come from `sources/<sha256>/`. A missing entry is fetched with the existing HTTPS client; an explicit
  `--source-archive <file>` seeds the cache **only if its SHA-256 equals the recipe's** — so offline and test runs do not
  need the network and cannot weaken verification.
* The pristine tree is extracted once and is read-only; each job gets a fresh copy under `builds/<job-id>/`.
* **Prerequisite found in this review:** zlib's archive is a `.tar.gz`, and the CLI archive module accepts only `xz` and
  `zip` (`unsupported archive format (expected xz or zip)`). Gzip is available in-process (the CLI links zlib already),
  so adding a hardened `tar.gz` reader (same path/link/size/entry-count limits and the same hostile-input tests as `tar.xz`)
  is the first implementation increment (**done 2026-11-07**, [record](../acceptance/sdk_install_acceptance.md#hardened-targz-reading-d3-step-1-linuxx86_64-2026-11-07)). Using the bundle's `tar` instead is rejected: extraction safety must not depend on
  a tool the same build is about to exercise.

### D3-7. Store item, build key, publish

* Build key: the formula in [crt_cli.md §5](crt_cli.md#execution-and-installation), with slice values: source SHA-256,
  recipe digest + adapter-table digest + test-source/shim digests, SDK content identity, host/target, external LLVM and
  `llvm-ar` identities, host-tools bundle identity, variant (`static`+`shared` produced together, as the recipe does),
  declared environment list. Zero target-port dependencies.
* Build in `builds/<job-id>/` staging, run the recipe tests and audits there, then publish by atomic directory rename to
  `ports/store/<build-key>/` with `manifest.json` (**CLI-owned experimental format 0**): input identities, file inventory
  with SHA-256, SONAME/aliases, runtime closure, tool versions, applied `post_configure_patch` reasons, test results,
  unsupported scope. Failed runs keep logs under `logs/`/`builds/` and never become a store item.
* Reuse of a store item re-validates inventory and key before use, as SDK `verify` does.

### D3-8. Audit and the consumer proof

Before publish: the shared object's `DT_NEEDED` set contains no host libc (the zlib recipe notes show this failure mode
on Linux); runpath/rpath point inside the SDK sysroot or the store item, never at the host (the executor therefore builds without `CRT_PORT_RPATH_DIR`, which `crt-cc` would stamp into every link); the `libz.so.1` SONAME and
symlinks exist; no file outside the staging prefix was written.

Consumption proof, for each of static and shared, from a project (not from the recipe's own test) that selects
provider `port`:

* build the recipe's `zlib_roundtrip.c` and a C++ consumer;
* static: the link evidence (linker map or trace) names `ports/store/<key>/lib/libz.a` and does not name the SDK `libz`;
* shared: the binary's runtime resolution (`LD_DEBUG=libs` or `/proc/self/maps` from a child run) names the store item's
  `libz.so.1` and not the SDK's; the process still prints the recipe's expected line;
* a content comparison is **not** a proof by itself: the SDK's zlib is produced by the same recipe and may be
  byte-identical, so path/resolution evidence is required;
* `sdk verify` on the SDK is unchanged before/after, and the process-observable SDK tree is never written.

## 3. Work breakdown (Linux/x86_64 first)

Status 2026-11-07: step 1 done ([record](../acceptance/sdk_install_acceptance.md#hardened-targz-reading-d3-step-1-linuxx86_64-2026-11-07)); step 2 done for the reader and the seeded table ([record](../acceptance/sdk_install_acceptance.md#recipe-subset-reader-d3-step-2-linuxx86_64-2026-11-07)), CRT review of the table pending; step 3 done ([record](../acceptance/sdk_install_acceptance.md#port-executor-d3-step-3-linuxx86_64-2026-11-08)); step 4 done ([record](../acceptance/sdk_install_acceptance.md#binary-audit-build-key-and-port-store-d3-step-4-linuxx86_64-2026-11-08)); step 5 done ([record](../acceptance/sdk_install_acceptance.md#project-provider-choice-and-consumer-proof-d3-step-5-linuxx86_64-2026-11-08)); step 6 done ([record](../acceptance/sdk_install_acceptance.md#oracle-differential-d3-step-6-linuxx86_64-2026-11-09)); the CLI command `port build|list|verify|recover` is done ([record](../acceptance/sdk_install_acceptance.md#port-command-d3-linuxx86_64-2026-11-09)).

1. Hardened `tar.gz` reading in the archive module + hostile-input tests (traversal, links, bombs, truncation).
2. Recipe reader for the §2 subset, with the exhaustive refusal tests, and the adapter table (CRT-reviewed) as data.
3. Job environment + executor (`configure` → `make` → `make install` through the host-tools bundle), including
   `post_configure_patch` and the recipe `tests`.
4. Binary audit and store publish/verify; build-key computation tests (every input changes the key).
5. Project integration: explicit provider choice and the consumer proof of §2 D3-8.
6. Oracle differential: run `crt-port-build.py` on the same SDK and compare the installed file inventory and test output.

Each step is a bounded increment with its own regression checks; none requires a published release, changes SDK
bytes, or moves a consumer lock.

## 4. Open questions that block no step above

* Whether the adapter table should later be signed with the registry snapshot (needs the official-trust work).
* Whether the shared audit should also assert the exact set of exported symbols against the recipe's version script.
* ~~How `crt-cc` behaves when its `sh` is the bundle's `mksh`~~: answered by the 2026-11-08 experiment in
  `docs/acceptance/sdk_install_acceptance.md` ("`crt-cc` under the bundle's `mksh`"): it runs, but the linker must be named explicitly
  and a `SHELL` path with spaces breaks `make`; both are step-3 executor requirements, and no compiler bridge is needed for them.

## 5. Failure handling expectations

Hash mismatch, unknown recipe digest, unsupported field, missing host tool, a `find` text not present, a failing test,
audit failure, interrupted build and concurrent builds of one key each produce a distinct non-zero result with a
machine-readable diagnostic; interrupted or concurrent runs must not publish a partial item or corrupt `sources/`.

## 6. Evidence this slice must record (acceptance, not here)

Per-step regression counts; the oracle differential; static and shared consumption proofs with the raw evidence
reference; SDK unchanged; exact CLI/SDK/LLVM/host-tools identities; every deviation and unverified item.

## 7. Keeping the Windows gate achievable

Nothing in §2 depends on a Linux-only mechanism except the proof commands. The executor takes all tool paths from the
host-tools bundle and the SDK (virtual shell paths versus native LLVM paths are kept distinct as the
[CLI design](crt_cli.md#execution-and-installation) already requires), and `target_overrides.windows` is parsed
(and refused unless the slice is run on Windows) rather than silently dropped. The Developer-Mode symlink requirement
for zlib's `libz.so` link, spaces and Korean characters in paths, and the Windows mksh/make behaviors documented in
`zlib.json` are the 4.2 gate's own tests.

## 8. macOS adapter policy (2026-11-09)

The same pinned zlib recipe and source are used; upstream files and SDK bytes are not patched. The compiled-in adapter
selects an OS-specific `port_layout`: macOS installs `libz.a`, `libz.dylib`, `libz.1.dylib` and `libz.1.3.1.dylib`.
The executor adds `LDSHARED=@CC@ -dynamiclib -install_name @rpath/libz.1.dylib -compatibility_version 1 -current_version 1.3.1`
and make command-line `AR=<declared archiver> ARFLAGS=rc`. These are explicit policy inputs to the macOS build key:
zlib's Darwin configure otherwise forces the host's `/usr/bin/libtool` and an absolute temporary install name.
The configured archiver's sibling `ranlib` is required and hashed. Apple `ar`/`ranlib`, as well as LLVM names, are accepted;
this does not grant an implicit `/usr/bin` fallback. Whitespace/metacharacters in archiver and OS SDK paths remain refused.

`SDKROOT` is the explicitly configured OS SDK (or the existing explicit provider's `external_os_sdk`), not an inherited
environment value. Its `SDKSettings.json` hash is an additional macOS key input; this identifies metadata, not every byte
of the vendor SDK. The location itself is not part of the key. Linux's adapter serialization and environment/key shape stay
unchanged. No shared recipe schema, SDK profile or project-lock version changes.

The audit reads thin 64-bit little-endian Mach-O load commands: CPU type, install name/alias, dylib dependencies and
`LC_RPATH`. Fat/32-bit/big-endian/malformed images, foreign ELF images, outside-item/SDK search paths, job-path leaks and
undeclared dylib dependencies are refused. The OS boundary is `/usr/lib/libSystem.B.dylib`; SDK/item dependencies are
relative names. This is an install-level bounded audit, not a general dyld resolver, code-signature verifier or exported-symbol audit.
The project consumer selects the OS layout; actual mapped images are observed through the existing public
`crt_dl_iterate_images` PAL, not Darwin APIs in CLI product code.

The oracle deliberately differs in two ways: its install name is its temporary prefix, and its `LC_RPATH` has an extra
`@loader_path` because the oracle sets `CRT_PORT_RPATH_DIR` during every link. The native executor leaves that variable
empty during build and sets it only for unpublished test executables. Static archive container metadata can differ
between `libtool` and `ar`/`ranlib`; member names and object bytes must still agree. Native replay and its limitations
belong to [acceptance](../acceptance/sdk_install_acceptance.md#source-port-d3-replay-macosarm64-2026-11-09).

## 9. Windows adapter policy (2026-11-09)

Windows is a default CLI platform, so the same pinned zlib recipe runs on it through the CRT shell and CRT-built `make` of the
selected host-tools bundle. The recipe's own `windows` overrides apply unchanged (`-U_WIN32 ...`, `RANLIB=true`); upstream source,
the SDK and the recipe are not patched. The adapter selects a `windows` `port_layout`: `libz.a`, the PE DLL `libz.so.1.3.1`
and the links `libz.so`, `libz.so.1` that zlib's own Makefile makes (Developer Mode, as before), `zlib.pc` and the headers.
The DLL keeps the POSIX spelling because the recipe and the SDK's own libz do; the audit reads PE, not the extension.

Executor policy, none of it a new recipe/SDK/lock format:

- **Shell spelling.** The CRT shell treats a backslash as an escape, so every path handed to configure/make, to the wrappers and to
  the build steps uses forward slashes. The job prefix therefore appears in `zlib.pc` with forward slashes; publication rewrites
  and forbids both spellings.
- **Tools with spaces.** `AR` and `RANLIB` are started like the compiler, through job-local scripts under `/crt-bin` that `exec`
  the real tool (`C:/Program Files/LLVM/bin/llvm-ar.exe`), so Makefile word splitting never sees the space. A job-rootfs link to the
  tool directory is not used: a restricted-token run was observed to be refused access through it.
- **OS SDK.** The import-library directory of the portable contract's `windows-um-import-libraries` kind is passed explicitly as
  `CRT_WINDOWS_SDK_LIBPATH`. The content (SHA-256) of `kernel32.lib` and `synchronization.lib`, the default system libraries of the
  compiler wrapper, is a Windows build-key input; the location is not. Linux and macOS key shapes are unchanged.
- **Recipe tests.** Test programs get `.exe`; the loader finds the port's DLL through a native `PATH` of the port's `lib/` followed by
  the SDK's `bin/` (the Windows loader has no run path, so nothing is stamped into the images).
- **Consumers.** `run`/`test` put each used port item's `lib/` before the SDK's `bin/` and `lib/` in the child's search path. The
  Windows SDK contract declares no shared `z`; a target asking for it gets a clear refusal instead of a silent fallback.

The audit reads 64-bit PE images: machine, DLL kind, export-directory DLL name, and the import and delay-import tables. An image the
reader cannot account for (32-bit, truncated, a directory or string outside the file) fails the audit instead of being skipped.
A dependency is accepted only when it is a Windows system DLL (`kernel32`, `ntdll`, `api-ms-win-*` and a short fixed list), a DLL in the
SDK's `bin/` or `lib/` (compared case-insensitively, like the loader), or a DLL this item exports. The host's C runtimes
(`ucrtbase`, `msvcrt`, `vcruntime`) are deliberately not on the list. The export name must equal the layout's name and exist beside
the image. ELF and Mach-O images in a Windows item, and PE images in a Linux or macOS item, are findings. Run-path and
POSIX mode-bit rules do not exist for PE and are not claimed; this is an install-level audit, not a loader emulator, an
export-symbol audit or an Authenticode check.

The oracle (`crt-port-build.py`) also installs `lib/z.lib`, a byte copy of `libz.a` for a later port's plain `-lz`. The executor has no
dependent ports in this slice and does not install it; the oracle test requires the copy to be byte-identical and nothing else to differ in
the file set. The executed policy and its limits are recorded in
[acceptance](../acceptance/sdk_install_acceptance.md#source-port-d3-windowsx64-implementation-and-replay-2026-11-09).
